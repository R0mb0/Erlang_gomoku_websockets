1. Introduzione

Il progetto in 3 concetti chiave:

  1. Architettura ad Attori e Disaccoppiamento: Il sistema è diviso in entità concorrenti isolate (i processi Erlang) che comunicano esclusivamente tramite scambio di messaggi asincroni.
  2. Coordinamento Generativo (Modello Linda): Lo stato fondamentale di persistenza delle mosse non è un database tradizionale, ma un Tuple Space centralizzato implementato tramite tabelle ETS in-memory.
  3. Ibridazione Pragmatica: Per superare i limiti intrinseci di blocco del modello Linda (che causerebbero deadlock dei server), abbiamo fuso lo spazio delle tuple con uno stato locale del server a tempo di accesso costante $O(1)$.

2. Il Cuore della Persistenza: tuple_space.erl

Il file tuple_space.erl implementa un comportamento gen_server che incapsula una tabella ETS (Erlang Term Storage) di tipo duplicate_bag. Questo server mette a disposizione le primitive fondamentali di Linda: out (scrittura), in (lettura distruttiva bloccante) e rd (lettura non distruttiva bloccante).

La parte più pregiata ed elegante di questo file è la gestione della coda dei processi in attesa (Waiting). Se un processo richiede una tupla con in o rd e questa non è presente, il server non risponde subito, ma "parcheggia" il client salvando il suo identificativo di chiamata (From). Quando arriva una nuova tupla tramite out, il server scansiona la coda e sblocca i client interessati.

tuple_space.erl Funzione Interna: process_waiting/3 
%% Scansiona la coda dei processi bloccati in attesa di una tupla coincidente
process_waiting([], _Store, Acc) ->
    lists:reverse(Acc);
process_waiting([{Type, Pattern, From} | Rest], Store, Acc) ->
    case ets:match_object(Store, Pattern) of
        [Tuple | _] when Type =:= in ->
            %% Trovata per il consumo: cancella la tupla e rispondi manualmente per sbloccare il client
            ets:delete_object(Store, Tuple),
            gen_server:reply(From, Tuple),
            process_waiting(Rest, Store, Acc);
        [Tuple | _] when Type =:= rd ->
            %% Trovata per la sola lettura: rispondi ma mantieni la tupla nell'ETS
            gen_server:reply(From, Tuple),
            process_waiting(Rest, Store, Acc);
        [] ->
            %% Nessun match corrente: il client rimane in coda
            process_waiting(Rest, Store, [Acc | {Type, Pattern, From}])
    end.

3. Il Server di Gioco: gomoku_server.erl

Il file gomoku_server.erl gestisce lo stato ad alto livello del gioco (il turno corrente, l'avvenuta vittoria e la validazione).

L'inghippo dei Deadlock risolto: Se usassimo il Tuple Space puro, per vedere se una cella è libera dovremmo fare una in cercando una tupla del tipo {cell, X, Y, empty}. Tuttavia, se la cella fosse occupata, quella tupla non esisterebbe e il nostro server rimarrebbe congelato (in deadlock) per sempre nell'attesa che qualcuno la reinserisca, bloccando tutte le successive richieste del WebSocket. Per evitare questo, il server di gioco implementa una Mappa locale dello stato (Board = #{}) che funge da specchio ottimizzato a tempo $O(1)$.

gomoku_server.erl Funzione Callback: handle_call({make_move, ...}, ...) 
handle_call({make_move, Player, X, Y}, _From, State) ->
    Board = State#state.board,
    if
        Player =/= State#state.current_turn ->
            {reply, {error, not_your_turn}, State};
        %% Controllo istantaneo in O(1) sulla mappa di stato locale del processo
        is_map_key({X, Y}, Board) ->
            {reply, {error, cell_occupied}, State};
        true ->
            %% Persistenza nel Tuple Space secondo il modello Linda
            tuple_space:out({cell, X, Y, Player}),

            %% Aggiornamento specchio locale per le prossime validazioni
            NewBoard = maps:put({X, Y}, Player, Board),

            case check_win(X, Y, Player, NewBoard) of
                true ->
                    {reply, {ok, {game_over, Player}}, State#state{board = NewBoard}};
                false ->
                    NextTurn = switch_turn(Player),
                    {reply, {ok, move_accepted}, State#state{current_turn = NextTurn, board = NewBoard}}
            end
    end;

4. Algoritmo di Vittoria Radiale (Gomoku Logic)

Scansionare l'intera matrice $20 imes 20$ ad ogni mossa sarebbe inefficiente ($O(N^2)$). L'algoritmo implementato in gomoku_server.erl è di tipo radiale ricorsivo. Prende la coordinata esatta della mossa appena inserita e calcola l'estensione lineare lungo quattro direttrici (orizzontale, verticale, diagonale principale e diagonale secondaria).

gomoku_server.erl Algoritmo Ricorsivo di Vincita 
check_win(X, Y, Player, Board) ->
    %% Le 4 direzioni fondamentali a raggiera
    Directions = [{1, 0}, {0, 1}, {1, 1}, {1, -1}],
    lists:any(fun({Dx, Dy}) ->
        %% Conta quante pedine uguali ci sono in un verso e nel suo opposto
        Count = 1 + count_directional(X, Y, Dx, Dy, Player, Board) +
                    count_directional(X, Y, -Dx, -Dy, Player, Board),
        Count >= 5
    end, Directions).

La funzione ausiliaria count_directional/6 effettua passi incrementali di coordinate finché trova elementi di proprietà dello stesso giocatore all'interno della Mappa, garantendo una risposta immediata a costo computazionale bassissimo.

5. Comunicazione in Tempo Reale: Cowboy & Process Groups

La comunicazione avviene tramite WebSocket gestiti dalla libreria Cowboy (gomoku_ws_handler.erl). Quando un utente apre la pagina web, la connessione si trasforma in un canale bidirezionale persistente.

Il meccanismo Pub/Sub tramite Process Groups (pg): Erlang possiede una libreria nativa chiamata pg (Process Groups) per gestire i canali distribuite in stile Publish/Subscribe. Quando un handler WebSocket viene creato, si iscrive al gruppo comune gomoku_arena. Quando un giocatore fa una mossa accettata, l'handler recupera tutti i PID dei client connessi e invia loro un messaggio Erlang interno per forzare l'aggiornamento simultaneo.

gomoku_ws_handler.erl Inizializzazione e Gestione Broadcast 
websocket_init(State) ->
    %% Iscrizione dinamica del processo corrente (l'handler) al gruppo globale
    pg:join(gomoku_arena, self()),
    {ok, State}.

websocket_handle({text, Msg}, State) ->
    try jsx:decode(Msg, [return_maps]) of
        CommandMap ->
            Action = maps:get(<<"action">>, CommandMap, <<"unknown">>),
            ResponseMap = process_command(Action, CommandMap),
            JsonResponse = jsx:encode(ResponseMap),

            %% BROADCAST: estrae i PID iscritti all'arena e distribuisce l'evento
            Pids = pg:get_members(gomoku_arena),
            lists:foreach(fun(Pid) -> Pid ! {broadcast, JsonResponse} end, Pids),

            {ok, State}
    catch
        _:_ -> {ok, State}
    end.

%% Gestisce la ricezione dei messaggi interni Erlang inviati dal ciclo foreach precedente
websocket_info({broadcast, JsonResponse}, State) ->
    %% Invia fisicamente il pacchetto JSON sul browser del client via WebSocket
    {reply, {text, JsonResponse}, State};

6. Fault Tolerance e Albero di Supervisione: gomoku_backend_sup.erl

Il concetto cardine di Erlang è "Let it crash" (Lascialo fallire). Invece di scrivere pesanti ed infiniti blocchi try-catch difensivi attorno a ogni singola riga, si isolano i processi e si configurano dei Supervisori pronti a riavviare i lavoratori in caso di anomalie non previste.

Nel file gomoku_backend_sup.erl viene configurata una strategia one_for_one con una tolleranza massima di 5 crash in 10 secondi.

gomoku_backend_sup.erl Inizializzazione delle Specifiche dei Figli (Child Specs) 
init([]) ->
    %% Se un processo figlio muore, riavvia solo lui (one_for_one)
    SupFlags = #{strategy => one_for_one, intensity => 5, period => 10},

    ChildSpecs = [
        %% Figlio 1: Il Tuple Space (Persistenza dei dati)
        #{id => tuple_space,
          start => {tuple_space, start_link, []},
          restart => permanent,
          type => worker},

        %% Figlio 2: Il Server di Gioco (Logica applicativa)
        #{id => gomoku_server,
          start => {gomoku_server, start_link, []},
          restart => permanent,
          type => worker}
    ],

    {ok, {SupFlags, ChildSpecs}}.

7. Il Frontend Reattivo & Logiche Anti-Cheat

Il file gomoku_game.html è un'interfaccia a pagina singola scritta in puro JavaScript ed accesa graficamente con le classi di utilità di Tailwind CSS. Sfrutta l'API nativa WebSocket del browser.

Per salvaguardare la correttezza del gioco a livello di rete, il client applica delle barriere reattive temporanee (Anti-Cheat e Concorrenza lato UI): disabilita i click ed i selettori di ruolo non appena la partita è dichiarata conclusa o durante l'attesa del turno avversario, intercettando gli stati move_accepted e game_over provenienti dal backend.
